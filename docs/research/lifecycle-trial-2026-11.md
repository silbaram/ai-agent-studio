# 수명주기 뼈대 시험: OpenSpec과 spec-kit (2026-11)

- 시험일: 2026-11-05. OpenSpec 1.16.0, spec-kit 1.3.0. 둘 다 MIT다.
- 방법: 시험 프로젝트의 `design/`과 `data/` 사본 두 벌에 각각 설치했다. 같은 기준 문장 여섯 줄을 OpenSpec은 `config.yaml`의 `context`에, spec-kit은 헌장에 넣었다. 에이전트 둘이 같은 시나리오를 돌렸다: 첫 기능, 범위 이탈, 설계 변경, 닫기와 다음 기능, 기계가 읽을 자리.
- 구현은 하지 않고 태스크까지만 만들었다. 기능 하나와 그 다음 기능, 모델 한 종류의 결과다.
- 아래 표의 기계 동작(검사 통과, 메타데이터, 명령 유무)은 사본에서 직접 재현했다. 산출물 분량과 에이전트의 판단은 시험 보고를 옮겼다.

## 결과

| 항목 | OpenSpec | spec-kit |
|---|---|---|
| 설치 | Node 22.12 이상, 패키지 57개, 17MB | uv, 48MB. 이 환경에는 pip도 uv도 없어 uv를 따로 받았다 |
| 첫 기능의 산출물 | 5개 파일, 128줄 | 8개 파일, 397줄 |
| 규칙 하나를 바꾼 뒤 손댄 문서 | 4개, 약 +21/−17줄 | 5개, +37/−32줄 |
| 닫기 | `archive`가 메인 스펙에 병합 | 없음. 상태 글을 손으로 바꿈 |
| 쌓이는 스펙 | `openspec/specs/`에 능력별로 쌓임 | 없음. 기능 폴더만 남고 다음 기능이 읽으라는 말도 없음 |
| 삭제 | 명령 없음 | 명령 없음 |
| 목록·상태 JSON | `list`, `status`, `validate`, `show`에 있음 | 없음. 파일을 직접 읽어야 함 |
| 변경별 메타데이터 | `.openspec.yaml`의 `x-` 키. strict 통과, 보관 뒤에도 남음. JSON 출력에는 안 나옴 | 자리가 없음. `feature.json`은 포인터 하나이고 키가 지워질 수 있음 |
| 문서 형식 검사 | 있음 | 없음. 빈 `spec.md`와 빈 `tasks.md`도 통과 |
| 한국어 | 본문은 됨. `## ADDED Requirements`, `### Requirement:` 같은 제목과 본문의 `SHALL`, `WHEN`, `THEN`은 영어 강제 | 제한 없음 |
| 범위 밖 변경 | `validate --strict`와 `archive` 통과 | 스크립트 전부 통과. LLM 단계 `/speckit-analyze`가 CRITICAL로 지적(1회, 권고일 뿐) |
| 설계 변경 감지 | 7개 명령의 출력이 전과 같음 | 스크립트는 못 봄. `/speckit-analyze`가 지적(1회, 헌장이 `design/`을 가리킨 덕으로 보임) |
| 사용 통계 | 기본 켜짐(명령 이름과 버전). `OPENSPEC_TELEMETRY=0`으로 끔 | 수집 코드를 찾지 못함(문자열 검색만 함) |

`/speckit-analyze`에 맞서는 OpenSpec의 `/opsx:verify`는 구현과 산출물을 비교하는 단계로, 기본 프로필에 없고 돌려 보지 않았다.

## 둘 다 못 하는 것

- 범위 이탈을 막지 못한다. 멈춘 것은 기준 문장을 읽은 에이전트의 판단이었고, 판단을 무시하면 끝까지 갔다.
- 스펙이 어느 설계를 근거로 했는지 남지 않는다. 설계가 바뀌어도 기계는 모른다.
- 시스템 id를 모른다. 없는 id를 적어도 통과한다.
- 규칙을 참조할 문법이 없다. 시험 가능하게 쓰라는 요구 때문에 규칙의 뜻이 스펙에 다시 적히고, 규칙 하나가 문서 네다섯 개로 번진다.

그래서 `scope-guard`는 어느 쪽을 골라도 이 저장소가 만든다. 뼈대 도구를 고르는 기준은 검사 능력이 아니라 가벼움과 붙일 자리다.

## 판단

OpenSpec을 골랐다(2026-11-05).

- 같은 기능의 산출물이 3분의 1 분량이다(원칙 7).
- 닫기와 쌓이는 스펙이 있어 게임이 커져도 현재 규격을 한곳에서 읽는다.
- 변경별 메타데이터와 JSON 출력이 있어 훅이 붙을 자리가 있다(원칙 1). spec-kit은 임의의 글 칸을 정규식으로 읽어야 한다.

치러야 할 비용:

- 한국어 문서에 영어 제목과 `SHALL`이 섞인다. `SHALL`은 문자열 검사라서 문장 끝에 덧붙이면 통과한다.
- `validate` 통과가 `archive` 성공을 뜻하지 않는다. 없는 요구사항의 MODIFIED는 `validate`가 INFO로만 알리고 `archive`가 거부한다.
- `archive --yes`는 미완료 태스크가 있어도 병합한다.
- Node가 필요하다. 없이 도는 단독 실행 파일(`openspec install`)은 시험하지 않았다.
- 사용 통계를 꺼야 한다.

spec-kit의 `/speckit-analyze`는 이번 시험의 유일한 내용 점검이었다. LLM 단계라 기계 검사를 대신하지는 못하지만, 같은 일을 시키는 절차는 OpenSpec 쪽에도 넣을 수 있다.

## 돌려 보지 않은 것

- 실제 구현을 동반한 `apply`와 `/speckit-implement`, `/opsx:verify`, `/speckit-converge`
- spec-kit의 `specify workflow run`과 사람 승인 게이트, 로컬 확장 설치, 커뮤니티 Archive 확장
- OpenSpec의 포크 스키마로 변경 만들기, 단독 실행 파일
- 기준 문장 없이 돌린 대조군, Windows
