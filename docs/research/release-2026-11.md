# 본 게임 제작에서 출시까지 조사 (2026-11)

조사일: 2026-11-22. 별 수와 최근 활동은 그날 `gh api` 기준이다. 문서만 읽었고 저장소의 코드는 실행하지 않았다.

표시: **✔** = 원문(저장소 파일, 공식 문서)에서 직접 읽음. **~** = 검색 결과, 2차 기사, 기억에 기댄 요약이라 원문 확인 안 함.

## 왜 조사했나

우리 스킬은 아이디어 → 브리프 → 시스템 → 시험판 → 판정 → 본 게임으로 넘어가기(엔진, 버리기/키우기, `_main` 다시 확인) → 그림 넘기기까지 다룬다. "본 게임 제작이 시작된 뒤"부터 "완성·출시"까지가 비어 있다. 다섯 가지를 물었다.

1. 콘텐츠 늘리기: 시험판·슬라이스 분량에서 전체 분량(카드, 적, 레벨)으로 늘릴 때 검증한 재미·밸런스를 깨지 않는 법. 회귀 검사(봇 다시 돌리기, 기준선 비교, "재미 회귀")가 있나
2. 판정 뒤 빌드가 바뀌면 그 판정이 낡았는지 어떻게 아나(빌드 지문, 다시 확인 계기)
3. 다듬기: `[가정]` 숫자를 플레이·원격 측정으로 잰 값으로 바꾸기, 디자이너 아닌 플레이어와 그 수
4. 출시 준비 게이트: 기능·콘텐츠 완료, 임시 숫자·에셋 없음, 에셋 라이선스, 개발 도구 제거, 실행·충돌 확인, 알파·베타·골드 정의와 끝내는 조건
5. 출시 뒤 조정(라이브 튜닝): 혼자·작은 팀 범위에 드는가

범위는 AI 에이전트로 만드는 혼자·작은 팀의 2D 게임이다.

## 공통으로 보이는 것

- **알파·베타의 뜻은 거의 같다.** 알파 = 기능(시스템) 완료, 베타 = 콘텐츠 완료 후 고침만, RC/골드 = 낼 수 있는 빌드. 끝내는 조건은 "남은 일의 종류"로 정한다(새 기능 없음 → 새 콘텐츠 없음 → 고침만). 숫자 문턱(충돌률, FPS, 커버리지 %)은 템플릿 칸으로만 있고 값은 비어 있다(CCGS milestone 템플릿 ✔).
- **콘텐츠를 늘릴 때 재미 회귀를 기계로 보는 곳은 abagames뿐이다.** 같은 시드·같은 봇으로 전후를 비교하고, 다른 값에서 끌어낸 상수를 다시 끌어내고, 쓰이지 않는 메커니즘을 찾는다. CCGS는 정적 비교(계획 수 대 실제 수, 값 대 목표 범위)에 머문다. 카드 게임에서는 "고른 비율 / 이긴 덱 비율"이 흔한 지표다(Slay the Spire ~).
- **"낡음"은 시간이나 파일 날짜로 판단하는 곳이 많다.** CCGS는 보고서가 코드보다 오래되면 낡았다고 본다. 더 정밀한 것은 둘: CCGS의 Keep 고정값(사람이 좋아한 값이 움직였나)과 abagames의 "사람에게 마지막으로 넘긴 빌드 이후 바뀐 값". 가설마다 기대는 값을 적어 두고 그것이 바뀌었을 때만 다시 판정하는 곳은 없다.
- **"확인하지 못함"은 통과가 아니다.** CCGS는 이 원칙을 모든 검사에 퍼뜨렸다: 결과 없음과 0건을 구분, 분모를 적음, `[?]` 표시. 우리 "하지 않은 확인은 통과가 아니다"와 같다.
- **외부 플레이어는 "관찰"과 "수치"를 나눈다.** 처음 보는 사람이 막히는 곳은 적은 사람(관찰, 반복)으로 찾고, 밸런스 수치는 판 기록으로 본다. 숫자를 근거 있게 낸 곳은 NN/g(사용성 5명, 수치 20명) 정도이고, 게임 판정에 쓸 수를 정한 곳은 없다. CCGS의 "3세션"도 근거가 적혀 있지 않다.
- **출시 확인 중 혼자 하는 작은 게임에 실제로 필요한 것은 짧다.** 깨끗한 환경에서 실행·종료, 실행 시 충돌 없음, 적은 기능이 실제로 동작, Release 빌드, 에셋 출처·라이선스와 AI 사용 표시, 빌드 식별자, 되돌릴 빌드. 스토어·마케팅·커뮤니티·서버 항목은 판매 목표일 때만 해당한다.
- **목표에 따라 게이트 크기를 바꾼다.** CCGS는 `full/standard/minimal` 축소와 `/cut`의 목표(hobby, sell, early_access, publisher)로 날짜·동결을 묻는지 정한다. 축소는 "있어야 할 것"만 줄이고 "동작해야 할 것"은 줄이지 않는다 ✔.
- **출시 뒤 조정은 큰 곳만 다룬다.** 작은 팀 자료가 말하는 것은 "패치에도 안정화 기간", "지금 빌드의 문제를 먼저", "베타 브랜치에 먼저 올리고 확인" 정도다. 시즌·이벤트·라이브옵스 팀은 범위 밖이다.

## 우리 스킬에 가져올 것

1. **콘텐츠 늘리기 회귀 검사.** 콘텐츠를 더할 때마다 버틴 가설의 봇 기준선을 같은 시드·같은 봇으로 다시 돌려 앞의 값과 나란히 보인다. 가설의 문턱 쪽으로 움직였으면 사람이 플레이할 이유가 된다(봇만으로 버팀을 다시 확정하지는 않는다). 새 항목은 지금의 `stat-budget`·`combat-balance` 목표 범위로 보고, 목표가 없는 값은 "판정 안 함"으로 남긴다. 판 로그가 있으면 "한 번도 안 골라짐 / 늘 골라짐"을 항목별로 센다. abagames의 "다른 값에서 끌어낸 상수 다시 끌어내기"는 지금 `[계산]` 출처 태그로 표현할 수 있다.
2. **판정이 낡았는지를 "바뀐 값"으로 본다.** 지금 빌드 지문(`cfg…`)은 설정 전체의 해시라 카드 하나만 더해도 모든 판정이 다른 빌드가 된다. 전체 분량으로 늘리는 동안에는 이것이 너무 거칠다. 가설마다 기대는 데이터 키(또는 시스템)를 적고, 사람이 마지막으로 플레이한 빌드 이후 바뀐 키 목록과 겹치면 "낡음 — 다시 판정", 겹치지 않으면 1번 회귀만 통과하면 이어 간다. CCGS Keep 고정값처럼 "사용자가 좋다고 한 값"을 고정해 두고 움직이면 알리는 것도 같은 틀에 들어간다. 지난 판 로그는 그 빌드의 증거로 두고 다시 만들지 않는다(abagames, 지금 `cut` 규칙과 같음).
3. **다듬기는 숫자를 확정하는 단계로 정의한다.** 남은 `[가정]` 숫자(지금 `check --fail-on-assumed`의 데이터 파일 gate 줄)를 `[측정]`(판 로그, 플레이) 또는 `[결정: 사용자 날짜]`로 바꾸는 것이 다듬기의 끝내는 조건이다. 화면·소리 다듬기는 규칙을 건드리지 않았음을 같은 시드 봇 결과가 같다는 것으로 확인한다(abagames). 다듬기 목록 줄마다 출처를 붙이고 지어낸 줄은 넣지 않는다(CCGS `from:`). 디자이너 아닌 플레이어는 "처음 보는 사람이 막히는 곳"(관찰)과 "가설 수치"(판 로그)를 나눠 기록하고, 사람 수는 사용자가 정하되 적으면 한계로 남긴다(지금 표본 줄이기 규칙과 같은 방식). 모집 경로는 브라우저 빌드(itch) 또는 Steam Playtest를 알려만 준다.
4. **짧은 출시 게이트, 목표별 크기.** 기본(취미·무료 공개):
   - 모든 `_main` 가설이 확정(버팀, 또는 사용자가 모름으로 둠)이고 그 뒤 바뀐 값이 2번 기준으로 낡지 않음
   - `check --fail-on-assumed`가 데이터 파일까지 PASS(숫자 `[가정]` 없음)
   - 계획한 콘텐츠 수와 `data/` 수가 같음(CCGS `content-audit` 방식, 기계로 셀 수 있음)
   - 에셋·코드 출처와 라이선스 목록이 있고 AI 생성물 표시가 정해짐(art-handoff·asset-sourcing 기록과 이어짐)
   - 출시 빌드에 판 로그·봇·디버그 기능이 없음을 빌드 결과물에서 확인(지금 "출시판에서만 뺀다"의 확인 단계)
   - 깨끗한 환경에서 설치·실행·한 판·종료가 되고 실행 시 충돌 없음, 화면 글이 지금 규칙과 맞음
   - 빌드 식별자가 게임 안에 보이고, 출시 빌드를 태그로 남김

   판매 목표일 때만 스토어·가격·플랫폼 심사 항목을 더한다. 확인하지 못한 줄은 `[?]`로, 통과가 아니다.
5. **세 이정표를 우리 검사에 묶는다.** 알파 = 브리프·시스템 설계의 모든 시스템이 본 게임에 있음 + `_main` 판정. 베타 = 콘텐츠 수 일치 + 이후 새 콘텐츠 없음(콘텐츠 동결) — 동결 뒤에는 고침만 하므로 2번의 다시 판정이 드물어진다. 출시 후보 = 4번 게이트. 이정표마다 결과는 지금처럼 진행 · 되돌아가기 · 그만두기, 기록은 `design/production.md` 한 곳에 이어 쓴다.

출시 뒤 조정(질문 5)은 넣지 않는다. 다만 패치도 1·2번 회귀를 지나서 내고, 원격 측정은 동의한 사람만 받는다는 두 줄만 둘 만하다.

## 피할 것

- CCGS 전체판 수준의 긴 목록(스토어·마케팅·커뮤니티·서버·법무·부서별 서명). 우리 범위에서는 판매 목표일 때만 일부
- 근거 없는 숫자: "플레이어 50% 이상이 막힘", "동결일은 목표일까지의 70%", 충돌률·FPS·커버리지 % 칸, "4시간 이상 장시간 시험"
- 파일 날짜만으로 "낡음"을 판단하는 것(콘텐츠를 늘리는 동안 모든 판정이 늘 낡아 보이거나, 반대로 아무것도 안 보임)
- 봇 결과만으로 재미 판정을 다시 확정하는 것, 지표만으로 조정하는 것(Slay the Spire도 불평·관찰과 맞춰 봄 ~)
- 규칙이 바뀐 뒤 예전 판 로그를 다시 만들거나 옮기는 것
- 사용성 "5명"을 밸런스 수치 판정의 표본으로 쓰는 것
- 혼자 만드는 작은 게임에 시즌·이벤트·라이브옵스 절차를 넣는 것
- 시험자를 홍보 명목으로 모아 무급 QA를 시키는 것, 리뷰를 부탁하는 것
- 라이선스 없는 자료(game-dev-foundry, Steamworks·NN/g 문서)의 문장을 옮기는 것. 구조와 생각만 참고한다. MIT/Apache 저장소에서 문장을 가져오면 `THIRD_PARTY.md`에 적는다
