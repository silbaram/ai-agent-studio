# 쉬운 안내

처음 보는 사람을 위한 설명이다. 설치 명령과 도구 명령은 [README](../README.md)에, 원칙과 경위는 [설계 문서](architecture.md)에 있다.

## 한 줄로

AI 에이전트(Claude Code, Codex)와 게임을 기획할 때, 에이전트가 "그럴듯해 보이는" 기획을 하지 않게 만드는 스킬 묶음이다. 아이디어, 수치, 레벨, 플레이 결과를 파일로 적게 하고, 그 파일을 계산기와 검사기로 확인한다.

## 왜 필요한가

AI에게 게임 기획을 맡기면 흔히 이런 일이 생긴다.

| 흔한 일 | 이 스킬들이 막는 방법 |
|---|---|
| 근거 없는 숫자를 지어낸다 ("보스 체력은 5000") | 숫자마다 어디서 왔는지 표시하게 한다. 지어낸 숫자는 `[가정]`으로 드러나고, 가정이 남으면 확정하지 못한다 |
| "재미있을 겁니다"라고 단정한다 | 재미는 사람이 직접 해 본 기록으로만 판정한다. 판정은 기록만 읽는 심판 에이전트가 제안하고(Claude Code), 확정은 사람이 한다 |
| 만들다 보면 처음 정한 범위를 넘어 기능이 늘어난다 | 기획의 범위(MVP)를 벗어나는 작업을 찾아 알린다. Claude Code에서는 훅이 그런 편집 앞에서 사용자에게 묻는다 |
| 아이템 하나를 고치면 다른 곳이 깨지는데 모른다 | 아이템, 적, 전투, 재화, 레벨 데이터를 한 번에 검사해 서로 어긋난 곳을 알려 준다 |

심판 에이전트와 훅은 Claude Code에서 `setup` 명령을 실행해야 생긴다. Codex에는 없으므로 범위 검사(`scope`)와 데이터 검사(`check`)를 직접 돌리고, 판정도 같은 절차를 에이전트가 직접 따른다. 이때는 만드는 쪽과 판정하는 쪽이 나뉘지 않는다는 것을 알고 쓴다.

## 큰 흐름

```text
아이디어
  → ① 구조가 다른 컨셉 후보 여러 개를 만들고 단순한 전략으로 반증해 본다
  → ② 사람이 하나를 고르면 브리프(설계 요약)를 쓴다
  → ③ 필요한 시스템과 만드는 순서를 정한다
  → ④ 그림 없는 시험판(회색 상자, 그레이박스)을 만든다
  → ⑤ 사람이 직접 해 보고 기록을 남긴다
  → ⑥ 가설을 판정한다: 버팀 / 틀림 / 모름
       버팀이면 ⑦ 수치와 레벨을 다듬고, 틀림이면 고치거나 다른 후보로 돌아간다
```

개발 작업은 OpenSpec 변경으로 나누고, 그 변경이 브리프의 범위 안에 있는지 `scope-guard`가 본다. [OpenSpec](https://github.com/Fission-AI/OpenSpec)은 이 저장소에 들어 있지 않은 외부 도구라 따로 설치하고 게임 폴더에서 `openspec init`을 한 번 해야 한다. 쓰지 않으면 이 부분만 빠지고 나머지 스킬은 그대로 쓴다. 수치와 레벨(⑦)은 시험판을 만들 때부터 함께 다듬어도 된다.

## 스킬 13개를 쉬운 말로

| 이럴 때 | 스킬 | 얻는 것 |
|---|---|---|
| 아이디어만 있다. 또는 이미 만들고 있는 게임을 정리하고 싶다 | `concept-exploration` | 후보 비교표, 고른 안의 브리프 |
| 게임에 어떤 시스템이 필요한지 정리하고 싶다 | `system-design` | 시스템 목록과 의존 관계, 만드는 순서 |
| 개발 작업이 기획 범위를 넘지 않게 하고 싶다 | `scope-guard` | 범위 밖 작업 목록, 범위를 넓히는 편집을 묻는 훅 |
| 문서 속 숫자가 어디서 왔는지 표시하고 싶다 | `numeric-provenance` | 출처 표시와 그 검사 |
| 직접 해 본 결과를 남기고 가설을 판정하고 싶다 | `playtest-verdict` | 플레이 기록, 판정 제안, 측정값 |
| 아이템, 적, 영구 강화 목록을 관리하고 싶다 | `progression-economy` | 한 곳에 모은 데이터와 검사 |
| 이 장비로 이 적을 몇 대에 잡는지 알고 싶다 | `combat-balance` | 단계 × 적 처치·버팀 표 |
| 레벨업 선택지와 빌드가 고른지 보고 싶다 | `run-growth` | 빌드끼리 비교한 표 |
| 티어별 아이템이 너무 세거나 약한지 보고 싶다 | `stat-budget` | 예산 곡선과 넘침·모자람, 새 항목 초안 |
| 강화와 합성을 설계하고 싶다 | `crafting-balance` | 단계별 기대 비용, 합성의 손익 |
| 재화가 언제 모이고 무엇을 언제 살 수 있는지 보고 싶다 | `economy-flow` | 단계별 수입과 구매 시점 |
| 방, 웨이브, 쉬는 곳을 배치하고 싶다 | `level-design` | 조우 표, 예산 대비 세기, 페이싱 |
| (모든 스킬이 함께 쓴다) | `studio-data` | 계산기, 검사기, 뷰어 |

## 스킬 이름을 외워야 하나

꼭 그렇지는 않다. 에이전트는 설치된 스킬의 설명을 보고 맞는 것을 스스로 고를 수 있다. Claude Code에서 스킬 이름 없이 "카드 게임을 만들고 싶은데 어디서부터 하면 되나"라고만 했을 때 컨셉 탐색을 골랐다(Codex에서는 아직 확인하지 않았다). 다만 늘 고른다는 보장은 없다. 에이전트가 스킬 없이 혼자 기획을 시작하거나, 특정 스킬을 쓰게 하고 싶으면 README의 사용 예시처럼 스킬 이름을 문장에 넣는다.

## 꼭 알아 둘 말

| 말 | 뜻 |
|---|---|
| 컨셉 | 게임 아이디어 하나. 점수를 매기지 않고, 시험해 볼 수 있는 가설로 적는다 |
| 브리프 | 고른 컨셉의 설계 요약. 경험 목표, 필러(꼭 지킬 것), 안티필러(하지 않을 것), 핵심 루프, 가설, 가장 작은 시험판, MVP와 범위 밖 |
| 가설 | "플레이어는 이렇게 할 것이다" 같은 문장과, 틀렸다고 볼 신호, 시험 방법을 함께 적은 것 |
| 회색 상자 (그레이박스, greybox) | 그림 없이 네모와 색으로 만든 시험판. 재미를 확인하는 데 그래픽은 필요 없다. 스킬 문서와 데이터에서는 그레이박스, `greybox`라고 쓴다 |
| 판정 | 기록으로 가설을 버팀·틀림·모름 중 하나로 보는 것. 모름은 실패가 아니다. 정확한 기준은 [판정 기준](../skills/playtest-verdict/references/playtest-record.md#판정) |
| 출처 표시 | 숫자 옆에 붙이는 `[가정]`, `[계산: …]`, `[측정: …]`, `[결정: …]` 표시. 지어낸 값인지, 계산했는지, 재었는지, 사람이 정했는지를 가른다. 정확한 규칙은 [numeric-provenance의 태그](../skills/numeric-provenance/SKILL.md#태그) |
| 경고와 확인 | 검사기가 이상해 보이는 곳에 경고를 낸다. 의도한 것이면 이유를 적어 확인 처리한다. 확인할 때의 값을 이유에 적어 두면 값이 더 나빠질 때 다시 경고한다. 오류는 확인으로 끌 수 없다 |
| 위협도, 예산 곡선 | 적이 얼마나 센지를 하나의 숫자로 낸 것과, 단계가 오를 때 그 숫자가 얼마나 커져야 하는지를 정한 선 |
| 뷰어 | 모든 데이터를 브라우저 탭으로 보는 읽기 전용 화면. 파일을 고치면 저절로 갱신된다 |

## 처음 30분 따라 하기

1. 게임 폴더에서 스킬을 설치한다([README의 설치](../README.md#설치)). Claude Code면 `setup` 명령도 한 번 실행한다.
2. 에이전트를 열고 하고 싶은 것을 말한다. 예: "혼자 만드는, 한 판이 짧은 카드 게임을 만들고 싶어. 어디서부터 하면 돼?"
3. 뷰어를 연다: `python3 .claude/skills/studio-data/scripts/studio.py view .`
   - Codex로 설치했으면 `.claude/skills` 대신 `.agents/skills`다.
   - Windows PowerShell과 WSL은 명령이 조금 다르다. [README의 Windows 절](../README.md#windows에서-쓸-때-powershell과-wsl)을 본다.
4. 후보 비교표를 보고 하나를 고른다. 에이전트는 대신 고르지 않는다.
5. 에이전트와 함께 브리프를 다듬는다. 묻는 것에는 아는 만큼만 답해도 된다. 모르는 값은 가정으로 남는다.
6. 시험판을 만들어 직접 해 본 뒤 "오늘 플레이한 것 기록해 줘"라고 말한다.

## 이미 만들고 있는 게임이라면

후보를 새로 만들지 않고, 지금 게임을 브리프로 적는 데서 시작한다. 게임의 의도(무엇이 재미여야 하는지)는 코드에서 읽을 수 없으니 에이전트가 묻는다. 수치가 코드에 흩어져 있으면 먼저 `data/*.json`으로 옮겨야 밸런스 스킬이 읽고 고칠 수 있다.

## 사람이 하는 일

- 컨셉을 고른다.
- 판정 기준(어디부터 틀렸다고 볼지)을 정하고, 판정을 확정한다.
- 직접 플레이한다. 봇이나 스크립트로 돌린 판은 기록에 봇이 돌린 판이라고 표시해야(`simulated: true`) 버팀·틀림의 근거에서 빠진다. 표시하지 않으면 사람이 한 판으로 센다. 기록을 맡길 때 봇이 돌렸다고 말한다.
- 범위를 넓힐지 정한다.

## 하지 않는 것

- 재미를 계산하지 않는다. 계산은 "설계 가정끼리 서로 맞는가"까지다.
- 게임 코드를 대신 설계하는 스킬이 아니다. 게임 코드는 평소처럼 에이전트와 만들고, 이 스킬들은 기획과 검증을 맡는다.
- 그래픽과 사운드는 다루지 않는다. 그래픽은 [game-art-skills](https://github.com/silbaram/game-art-skills)가 맡고, 이 저장소와의 연결은 보류 중이다.
