# 설계

## 목표

게임 프로젝트를 기획부터 완성까지 AI 에이전트와 함께 관리하되, 개발이 처음 의도에서 벗어나지 않게 한다. 그래픽은 게임성이 완성된 뒤에 입힌다.

기준이 되는 게임 스튜디오 스킬(Claude-Code-Game-Studios, agentic-gamedev-skills)에서 좋은 점만 가져와, 더 가볍고 기계로 확인되는 형태로 만든다. 근거와 가져올 것·버릴 것은 [조사 문서](research/)에 있다.

## 첫 대상

- 장르: 첫 시험 프로젝트는 액션 로그라이크 + 메타 성장형(새로 만드는 게임), 두 번째는 턴제 격자 전술(스킬 없이 먼저 만든 게임에 기존 게임 경로로 붙임)이다. 스킬은 어떤 장르에도 쓸 수 있게 만들고, 시험 프로젝트로는 동작만 확인한다.
- 엔진: Godot, Unity, Unreal, Roblox 모두 고려. 그래서 도구는 엔진 중립 데이터(JSON/CSV)만 다룬다. 엔진별 연결은 얇은 어댑터나 안내 문서로 둔다.

## 층 구조

```
[수명주기 뼈대]  기획 → 설계 → 태스크 → 구현 → 검증
                 OpenSpec + superpowers식 실행 규율 (외부 도구)

[게임 설계 층]   컨셉 탐색·반증, 시스템 설계, 레벨,
                 아이템·경제·밸런스 기획(스탯·전투 계산, 예산 곡선, 강화·합성, 재화 흐름),
                 재미 검증 게이트
                 ← 이 저장소가 만든다

[그래픽 층]      도트·메시·VFX 제작과 검수
                 ← silbaram/game-art-skills (기존)
```

일반 수명주기 도구는 기능을 스펙으로 쓰고 구현하는 데 강하지만 재미·레벨·밸런스·아이템을 다루지 않는다. 이 저장소는 그 빈틈만 채우고, 뼈대는 검증된 도구를 쓴다. 근거는 [수명주기 도구 조사](research/landscape-2026-11.md)를 본다.

## 원칙

1. **기계로 강제할 수 있는 것은 스크립트로.** "하지 마라"는 문장보다 검사기·훅·CI를 우선한다. 에이전트가 수치를 암산하지 않는다. 처치 시간, 기대 비용, 확률은 도구가 계산하고 결과 파일을 출처로 남긴다.
2. **모든 수치에 출처 태그.** `[가정]` / `[계산: …]` / `[측정: …]` / `[결정: 누가 날짜]`. 가정이 남으면 확정 판정 금지. `[결정]`은 사용자가 정한 잣대(판정 문턱, 목표 범위, 규칙 상수)이고 게이트를 막지 않는다. → `skills/numeric-provenance`
3. **재미 검증은 증거가 있어야 통과.** 실행 기록, 플레이 기록, 텔레메트리 없이 "재미있다"를 판정하지 않는다. unknown은 실패와 구분한다. → `skills/playtest-verdict`
4. **만드는 쪽과 판정하는 쪽을 권한으로 분리.** 판정 역할은 읽기 전용으로 둔다. Claude Code에서는 판정 에이전트의 쓰기를 훅으로 막는다(`studio.py setup claude`).
5. **밸런스는 곡선에서 표로, 하나의 스탯 모델로.** 항목을 하나씩 감으로 정하지 않는다. 티어·구역별 예산 곡선과 원형을 먼저 정하고 표는 거기서 만든다. 아이템 점수와 몹 위협도를 따로 매기지 않고, 같은 스탯과 공식으로 "이 장비로 이 몹을 몇 초에 잡나"를 계산한다.
6. **스킬은 마크다운, 도구는 Python 표준 라이브러리.** bash 의존 없이 Windows에서도 동작하게 한다. 테스트는 `unittest`. 파이썬 코드와 뷰어는 공용 스킬 `studio-data` 한 곳에 두고, 다른 스킬은 절차 문서만 둔다.
7. **가볍게.** 단계는 필요한 만큼만 쓴다. 설정 항목을 늘리지 않는다. 공식은 정해진 형태 중에서 고르게 하고, 임의 수식 실행기는 만들지 않는다.
8. **영문 ID, 한국어 설명.** 스킬 이름·태그 키워드·파일명은 영문 규칙, 본문은 한국어.
9. **그래픽 유보.** 회색 박스 증거를 인정하고, 마지막에 game-art-skills로 넘길 인계 정보를 만든다.

### 3단계: 밸런스 기획

| 단계 | 내용 | 상태 |
|---|---|---|
| B1 | **공통 스탯 모델과 전투 계산.** 스탯 역할(체력·공격·방어·공속·치명) 연결, 방어 공식(고정값·비율·레벨 비율·직접 퍼센트 중 게임마다 선택), 단계별 기준 장비. 몹별 처치 시간과 버티는 타격 수를 계산하고 목표 범위를 벗어나면 경고 (`combat-balance`) | 1차 완료 |
| B2 | **예산 곡선과 표 제안.** 티어·구역별 스탯 예산, 아이템 종류(원형)별 예산 배분, 몹 원형. 곡선에서 표 초안을 만들고 곡선 이탈을 검사, 전투 공식으로 스탯 원가 제안 (`stat-budget`) | 1차 완료 |
| B3 | **아이템 강화와 합성.** 강화 단계별 효과·비용(·성공률), 합성 규칙. 원하는 티어까지의 기대 비용, 합성으로 가치가 불어나는 고리, 도달할 수 없는 아이템을 검사 (`crafting-balance`: 레시피와 무작위 합성 모두 지원) | 1차 완료 |
| B4 | **재화 흐름.** 구역별 수입(처치 보상·드랍)과 가격·강화비. 구매까지 걸리는 시간, 남는 재화 (`economy-flow`) | 1차 완료 |
| B5a | **판 안 성장.** 레벨업 선택지와 빌드 정책(우선순위·고르게)으로 단계별 스탯을 시뮬레이션해 B1 전투 계산에 더하고, 빌드끼리 비교해 모든 곳에서 밀리는 빌드를 경고 (`run-growth`) | 1차 완료 |
| B5b | **메타 성장을 전투 수치로.** 시뮬레이터의 전투 계산 모델: 단계마다 산 영구 강화의 스탯과 판 안 성장을 B1 전투 계산에 더해 처치·버팀 여유로 생존을 정하고, 수입·구매 순서는 B4 재화 흐름에서 읽음 (`simulate`, `"model": "combat"`) | 1차 완료 |
| B5c | **플레이 기록으로 보정.** 세션의 단계 기록으로 단계별 레벨·길이·처치 수·수입과 통과율을 가정과 비교하고, 기록에 맞는 생존 곡선 값을 제안. 옮긴 값에 출처를 남김 (`calibrate`, `playtest-verdict`) | 1차 완료 |

시험 프로젝트에서 B1~B5a를 써 본 뒤(2026-11-03) 스킬 사이를 이었다: 스탯 예산의 원가를 아이템·적 검사의 예산 가중치로, 강화 단계를 전투 기준 장비에, 레벨업 선택지가 아이템을 주게, 재화 흐름 단계를 전투 단계에(`combat_stage`), 판 사이 재화를 메타 성장 설정에(`meta_config`). 아직 남은 것:

- 무기마다 따로인 공격(무기 여러 개를 동시에 쓰는 게임). 지금은 주무기 하나를 기준 장비로 두는 대안만 있다.
- 경험치 곡선에서 빌드별 레벨 계산. 지금은 빌드의 `level_at`에 가정으로 적는다.

### 4단계: 레벨·시스템 설계

| 단계 | 내용 | 상태 |
|---|---|---|
| L1 | **조우 구성과 위협도 예산.** 레벨을 조우 순서로 적고, 조우의 위협도를 곡선 × 역할 배수의 예산과 비교. 놓은 적을 전투 단계와, 처치 수를 재화 흐름과 맞추고, 단일 대상 처치 시간을 단계 길이와 견줌 (`level-design`) | 1차 완료 |
| L2 | **페이싱.** 휴식·보상 배치, 강한 조우가 이어지는 구간, 보상 간격. 적이 없는 구간을 조우로 적기, 조우의 시각과 길이(재화 흐름의 단계 길이·구매 시점과 맞추기), 회복 지점 사이의 누적 소모(L1 시험의 73, 74, 81번). 별도 스킬 없이 `level-design`과 `levels.json`을 넓혔다 | 1차 완료 |
| L3 | **그레이박스 확인 목록.** 레벨마다 그래픽 없이 확인할 항목과 플레이 기록 연결 (`level-design`) | 1차 완료 |
| S1 | **시스템 설계.** 시스템의 규칙과 의존 관계를 브리프의 필러·범위에 연결 (`system-design`) | 1차 완료 |

- 133번: 단계 중간에 산 장비가 기준 장비에 없어도 말하지 않는다. `gear_before_purchase`는 반대 방향만 본다.
- 136번, 145번, 154번: 순서가 자유로운 게임을 표시하는 키가 없어 스테이지 선택형에서 읽지 말아야 할 값(앞 단계 대비, 판 전체 위협도, 임무를 넘는 보상 구간, 대표가 아닌 등급의 옮길 값)이 그대로 나온다. 문서로만 알린다.
- 148번: 확인한 구간의 값이 커져도 끝이 그대로면 확인이 풀리지 않는다. 확인할 때의 값을 저장하는 형식이 필요하다.

## 실제 한 사이클 (2026-11-07)

시험 프로젝트에서 사용자 없는 Claude Code 세션(`claude -p`)이 OpenSpec 변경 하나로 회색 상자(HTML/JS)를 만들고, 사용자가 실제로 플레이하고, 판정 에이전트가 두 가설을 판정했다. 변경 만들기, 시스템 연결, 구현, 플레이 기록, 판정이 한 번에 이어졌다. 범위 훅은 막을 일이 없었고, 판정 에이전트 훅은 셸 연결을 설계대로 막았다. 문서 시험에서 보이지 않던 이슈 225~236번이 나왔다.

고친 것: 가설의 id와 최소 표본(`sample`) 경고, 표본이 모자란 확정 판정 오류(227, 236번), 반대 방향·섞이는 변수·지표 정의를 쓰는 법(235번), 프로토타입 범위의 원본(229번), `runlog --group-by`와 묶음의 `variant`(228번), 계산 결과 파일과 판정 에이전트(234번), 잇지 않은 시스템의 규칙 참조 오류(232번), 단계 길이를 넘는 처치 시간 경고(230번), OpenSpec 설정의 한국어 `SHALL`과 이어서 하는 지시(225, 226, 231번).

뒤로 넘긴 것:

- 233번: 경험치 곡선을 담을 데이터가 없다. 레벨 속도를 프로토타입이 가정으로 정한다.

### 3차: 되돌리기 (2026-11-08)

틀림으로 확정된 `density_timing`을 두고 규칙 하나(적이 밟으면 보석이 깨진다, 유예 1초)를 바꿔 다시 시험했다. 단계 6의 되돌리기를 처음 끝까지 돌렸다. 열린 변경을 닫고, 브리프를 고치고, 새 변경으로 시험판에 넣고, 9판을 다시 판정했다. 판정 에이전트는 `density_timing`을 버팀으로 제안했다(1배 구간 안 상관 -0.399). 사용자는 모름으로 낮춰 확정했다. 깨짐 규칙이 적이 많은 곳의 늦은 보석을 없애기 때문이다. 이 기록으로는 플레이어의 선택과 규칙의 효과를 가를 수 없었다. 적을 보지 않는 봇도 같은 빌드의 1배에서 -0.3 안팎으로 문턱 -0.2를 넘었다. 부화는 9판 모두 0회여서 `hatch_risk`의 사망 쪽은 사건이 생기지 않았다.

### 밸런스 기록 대조 (2026-11-08)

밸런스 스킬을 실제 플레이 기록에 처음 대 봤다. 회색 상자 4세션 20판을 썼고, 사용자 없는 새 세션이 스킬 문서만 보고 비교했다. 데이터는 고치지 않았다. 설계 모델은 첫 구역 통과를 99.5%로 예측했지만, 깨짐 규칙 빌드의 실측은 33%였다. 5분이 끝날 때의 레벨은 가정 10, 실측 5였다. 처치 속도는 분당 약 50마리를 가정했고 실측은 36마리였다. 적 하나와 맞설 때 버티는 타수는 기록과 맞았다. 차이는 적이 쌓이는 데서 났다. 그런데 calibrate가 가장 큰 차이(끝 레벨)를 보지 못해 세션이 스크립트로 따로 냈다. 단계 하나짜리 시험판을 받지 못하는 곳이 이슈 276~282번으로 나왔다.

고친 것:

- 판이 끝날 때의 레벨(`level_end`)을 runlog가 모으고, 다음 단계의 `level_at`과 비교한다(278번).
- 실패한 판까지 센 처치 속도(`kill_rate`)를 모으고 비교한다. 넘긴 판이 3판보다 적거나 들어간 판의 절반보다 적으면 처치·수입·길이 비교를 참고로 낮춘다. 들어간 판은 그 값을 적은 기록만 센다(277번).
- 시간이 다 되면 끝나는 단계(`timed`)는 길이를 비교하지 않는다. runlog는 짐작하지 않는다. 길이가 모두 가정과 같으면 적으라고 알린다(276번). 샘플처럼 합성한 기록은 길이가 모두 같아 짐작하면 틀린다.
- `calibrate --variant 열=값`으로 시험 조건별로 본다(280번).
- 생존 곡선 제안이 기록이 없는 단계의 예측도 바꾸면 그 단계를 적는다. 지금 값의 4배를 넘으면 모델이 담지 못하는 것을 값이 메우는지 보라고 알린다(279번).
- 그레이박스 확인 항목 없이 그 단계를 플레이한 기록이 있으면 참고 줄을 낸다(281번). runlog가 모으지 않는 값은 스크립트와 결과 파일을 남겨 계산값으로 적는다(282번, 문서).

### 4차: 레벨업 체감 (2026-11-08)

사용자가 시험 주제를 레벨업 체감으로 바꿨다. 사람이 플레이하기 전에 봇으로 먼저 쟀다. 피해 강화 +2는 4번째 선택까지 일반 적의 처치 타수(2타)를 바꾸지 못했다. 사람의 3차 9판은 그 문턱에 한 번도 닿지 않았다. 스킬은 이것을 알리지 못했다. 강화 수치를 고치고, 판 끝 O/X 답과 살아 있는 적 수 로그로 가설 `levelup_felt`를 더해 6판을 했다. 플레이가 부담스러워 9판 계획을 5판째 뒤에 줄였다. 판정 제안은 `levelup_felt` 버팀이 처음으로 나왔다. 그런데 기록 에이전트가 요약을 읽은 뒤 세 가설의 표본을 모두 줄였다. 그래서 기존 가설 하나가 모름에서 틀림으로 바뀌었다.

그 현장 시험의 283~299번을 고쳤다.

- 첫 단계에서 첫 선택이 일반 적의 처치·버팀을 바꾸지 못하면 `pick_no_effect`로 알린다. `--table growth`에 단계 안 레벨업 수만큼 고를 때의 타수(`2 → 2 → 2 → 2 → 2 → 1`)를 보인다. 확률 스탯(치명타)은 보지 않는다. 뒤 단계는 앞 단계의 성장을 넣지 않은 값이라 표에만 둔다(283, 284번). 한 단계에서 빌드 스탯이 같아지면 참고 줄을 낸다(285번).

- 문서로 고친 것: 범위 안의 구현을 시켰으면 propose 뒤 apply로 이어 가고, 게임 파일은 Write/Edit로만 고친다(286, 291번). 구조화한 자기 보고와, 자기 보고만으로는 버팀을 내지 않는 규칙(288번). 주장이 맞는 쪽 기준선도 여러 정책으로 낸다(289번). 가설을 더하면 성공 기준도 맞춘다(290번). cut은 기준을 고친 바로 다음 편집에서 한다(294번). 판정 에이전트는 `cd`를 붙이지 않는다(298번). 287번은 스킬 밖이다.

### 게이트 통과 길 (2026-11-09)

가설이 버틴 뒤의 길을 처음 끝까지 가 봤다. 판정 확정 → 측정값 올리기 → calibrate → 게이트 순서다. `levelup_felt` 버팀을 확정했고, 4차 표본 축소는 가설마다 사실대로 적었다(나머지 두 가설은 9판 기준으로 되돌려 모름). 측정값으로 옮긴 값은 0개라 게이트는 그대로였다. 확실한 측정값(1구역 일반 적 처치 250)이 있어도, 출처가 항목 단위라 같은 항목의 다른 가정값과 함께 올릴 수밖에 없었다. 4단계로 게이트가 줄어들 수 없는 구조였다. 이슈 300~304번이 나왔다.

- 값마다 출처를 적는 `provenance.fields`(칸 경로마다 kind·source)를 더했다. 모든 수치 칸에 가정이 아닌 출처가 붙으면 그 항목은 게이트에서 빠진다. 그 전에는 게이트 줄에 `zone_1(필드 1/4)`로 보인다(303번).
- 절차 이탈에 `hypotheses`를 적으면 그 가설의 판정에만 센다(301번).
- 시험 조건을 섞은 calibrate는 조건마다 다시 비교한다. 둘 이상의 조건이 같은 쪽으로 다를 때만 ⚠를 붙이고, 아니면 "조건마다 다름, 참고"로 둔다. 섞어 맞춘 생존 곡선 제안도 참고다(302번).
- `runlog --timed 단계`로 시간 제한 단계를 적는다(304번). 사용자가 정하지 않은 표본 축소는 결과 전 기준으로 되돌린다(300번, 문서).

### 게이트 길 재시험 (2026-11-09)

값마다 출처를 적을 수 있게 된 뒤 4단계를 다시 했다. 에이전트가 1구역 일반 적 처치 250 하나만 `provenance.fields`로 측정에 올렸다. 4차에서 5분을 채운 5판이 설정과 관계없이 모두 250이었다. 게이트는 `zone_1(필드 1/4)`로 진행을 보였지만 여전히 실패했다. 스킬은 판정 문턱과 기획 목표를 의도라며 `[가정]`으로 두라고 했고, 게이트는 `[가정]`을 막았다. 그래서 끝까지 해도 통과할 수 없었다(306번). 이슈 305~307번이 나왔다.

- 출처 종류 `[결정: 누가 날짜]`(데이터는 `decided`)를 더했다. 사용자가 정한 잣대(판정 문턱, 기획 목표 범위, 규칙 상수)이고 게이트를 막지 않는다. 플레이로 맞는지 볼 수 있는 값(적 체력, 보상)은 사용자가 골랐어도 `[가정]`이다. 에이전트는 스스로 `[결정]`을 달지 않는다. 날짜가 없으면 오류다. 태그 꼴만 바꾸면(`[가정: 메모]`, `[assumed]`에서 `[결정]`으로도) 판정 기준 지문은 그대로이고, 그 전에 기록한 지문도 맞는 것으로 본다. 시뮬레이터 설정은 모델 값이라 결정으로는 게이트를 넘지 않는다(306번).
- 섞은 조건의 평균이 가정과 맞아도, 조건마다 가정의 양쪽으로 크게 갈리면 참고로 둔다(305번).
- 넘긴 판의 처치가 레벨에 놓인 적 수와 같으면 공급이 처치를 묶었다고 알리고, 처치 시간 경고를 기록으로 확인할 길을 안내한다(307번).

### 사용자가 정한 잣대 (2026-11-09)

사용자가 숙성 보석 브리프의 판정 잣대를 지금 값 그대로 정했다. 에이전트가 사용자의 실제 결정을 `[결정]`으로 적은 첫 경우다. 새 세션은 "판정 잣대"라는 말을 문턱(`failure_signal`, 성공 기준)으로만 읽고, `test`의 표본·구간·5분 판은 정했다는 말이 없다며 되물었다. 이어서 사용자가 test 값도 정했다고 하자 그것도 바꿨다. 태그 30개를 바꿨고 판정 기준 지문은 그대로였다. 게이트에서 브리프 줄이 처음으로 빠졌다. 그런데 태그가 없던 "모두 6판"에는 결정을 적을 수 없었다. 태그를 새로 달면 지문이 바뀌어 `levelup_felt` 버팀 판정이 지난 판정이 되기 때문이다. 이슈 309~313번이 나왔다.

- 판정 기준 지문은 출처 태그와 띄어쓰기를 빼고 계산한다. 태그를 달거나 지우거나 종류를 바꿔도 지문은 그대로다. 예전 두 꼴(태그 꼴을 맞춘 것, NFC만 맞춘 것)로 기록한 판정도 맞는 것으로 보고, `check`가 지금 꼴의 지문을 참고 줄로 알린다. 태그를 달기 전에 그 지문으로 바꿔 둔다(312번).
- 그래서 태그를 지운 것은 지문으로 알 수 없다. 대신 판정 기준 문장(가설의 claim, failure_signal, test와 성공 기준)의 태그 없는 수치(단위 없는 -0.2 포함, 5판째 같은 순서는 빼고)를 경고하고 게이트에서 막는다(312번).
- 게이트 줄이 칸 안에 남은 값을 보인다: `test(가정: 60초, 3개; 태그 없음: 6판)`(310번, 쉼표로 가른 것은 314번).
- `test`의 시험 설계 값(표본, 구간·창, 재는 간격, 세는 범위)도 사용자가 정하는 잣대다. "판정 잣대"라고만 하면 어디까지인지 묻는다. 한 가설의 두 칸(또는 가설과 성공 기준)에 같은 값이 있는데 한쪽만 `[결정]`이면 `criteria_tag_mismatch`(309번).
- 판정 글에는 문턱을 태그 없이 쓴다(판정 에이전트 지침에도 적었다). `check`는 `next_needs`, 뷰어는 `reason`과 `next_needs`의 가정·결정 태그를 빼고 보인다(311번). 태그를 안내하는 문구가 `[결정: 누가 날짜]`도 말한다(313번).

지문 바꾸기 현장 시험(같은 날)에서 에이전트는 참고 줄을 보고 판정 지문을 먼저 바꾼 뒤 태그를 달았다. 그때 나온 것을 고쳤다.

- 태그는 같은 문장 안에서 찾는다. 다음 문장의 태그가 앞 수치를 통과시키지 않는다. 경고와 게이트 줄은 보이지 않은 값을 `외 N개`로 알리고, `--json`의 `values`에 전부 낸다(315번).
- 가운뎃점 목록(`0.5·1·2배`)은 범위처럼 수치 하나다. 판정 기준 문장에서는 부호 붙은 수(`+10`)도 수치로 본다(314번, 316번).
- 빌드의 게임 수치는 판정 기준에 옮겨 적지 않고 빌드 id나 변경 이름으로 가리킨다. `--fail-on-assumed`에서 판정 기준 문장에 `[가정]`이 남으면 게이트 아래 참고 줄이 잣대인지 게임 수치인지 가르는 길을 알린다(316번).
- `check`가 브리프의 `[계산]`·`[측정]` 경로 출처를 md의 `--check-paths`처럼 확인한다. 기준은 게임 프로젝트 폴더다(317번). 합친 기록(`#pt_a, pt_b`)은 세션마다 확인한다.
- 검토에서 고친 것: 수치를 감싼 괄호가 닫힌 뒤의 태그도 그 수치의 것이 아니다(315번의 제안). 영문 줄임말은 문장 끝이 아니다. 부호는 단위 수치에도 들어간다(`+3초`). 값 꼴이 바뀌어도 예전 값(`2배`, `0.3`)으로 적은 `criteria_tag_mismatch` 확인은 이어 쓴다. 경고와 게이트 줄은 같은 수(5개)를 보인다.
- 옮겨 적은 게임 수치 정리 현장 시험(같은 날): 에이전트는 참고 줄대로 test의 게임 수치를 지우고 사용자 확인을 받아 판정 지문만 바꿨다. 그때 나온 것: 판정한 가설의 문장은 고치기 전에 확인을 받아 문장과 `criteria`를 한 번에 바꾼다(318번). `verdict_criteria_changed`는 뜻이 바뀌었는지부터 가리게 하고 뜻이 같은 고침의 예에 옮겨 적은 수치를 지운 것을 든다(319번). 데이터 파일의 지금 값이 아니라 빌드를 가리킨다(320번). 지문을 바꾼 기록이 판정에 남지 않는 것은 297번(기준 이력 칸)으로 남긴다.
- 컨셉 되돌리기 현장 시험(같은 날, 2026-11-08 기록의 복사본): 에이전트는 시험판 변경을 닫고 상태·탈락·다음 후보를 물었지만, 승인을 내리는 편집은 범위 훅이 물어 확인 창이 없는 실행에서 거부됐다. playtest-verdict에 '컨셉을 되돌릴 때' 순서를 두었다: 묻기 → 상태 바꾸기(훅이 묻는다) → 시험판 변경을 합치지 않고 닫기 → 설계와 데이터는 다음 컨셉까지 두기 → 선택 단계(321번, 323번). 확정 판정인데 지문 때문에 걸린 가설은 게이트 줄에 `(지문 없음)`, `(기준 바뀜)`이 붙는다(322번).
- 되돌리기 다시 시험(같은 날, 새 복사본): 에이전트가 먼저 묻고, 상태가 바뀐 뒤에 변경을 닫고, 설계와 데이터를 남겼다. 되돌린 컨셉의 판정 경고는 게이트를 말하지 않는다(324번). 닫는 명령에 확인 창이 없으면 `--yes`(325번). 선택한 컨셉이 없고 되돌린 컨셉이 있으면 `check`가 게이트의 다른 데이터 항목은 지난 기록이라고 알린다(326번). 다시 고를 때는 남은 후보를 모두 보이고 좁힐지는 묻는다(327번).
- 기준 이력(297번, 2026-11-10): 판정한 뒤 가설 기준을 고치면 가설의 `criteria_history`에 고친 칸의 고치기 전 값과 그때 지문을 남긴다. 판정 에이전트는 git을 볼 수 없어 고치기 전 기준을 여기서 읽는다. `check`가 이력을 거꾸로 덮어 지문을 다시 계산해 맞춰 보고(`criteria_history_mismatch`), 기준이 바뀐 판정의 경고는 그때 기준이 이력에 있는지 알린다. 이력은 지문과 게이트에 들지 않는다.
- 기준 이력 현장 시험(2026-11-10, 실제 기록): 새 세션이 문서만 보고 어제 고친 기준을 이력에 바르게 남겼다. 그때 나온 것: 고칠 때 남기지 못한 이력을 나중에 남기는 법(고친 날, 고친 커밋의 부모에서 가져올 값, `cut` 판정의 지문도 항목으로, 328번). 판정 기준 문장이 게임 데이터 파일을 가리키면 `criteria_points_to_data`로 경고한다. 파일 종류는 내용으로, 파일이 없거나 깨졌거나 게임 고유 형식이면 이름으로 본다. 같은 파일의 다른 꼴(`./`, 절대 경로)은 한 대상이다. 게이트는 막지 않는다(329번). 실제 기록에서 이 경고를 고친 세션은 `game_build` 칸이 없는 기록을 보고 변경 이름만 남겼다. 빌드 id는 세션의 `build` 커밋이나 `game_build` 지문이다. 판정한 가설에서는 `builds`를 새로 더하지 않고(세는 판을 바꿀 수 있다) 문장의 변경 이름으로 가리키며, 이름이 없으면 묻는다고 경고와 문서에 적었다. 이 안내는 가설 문장의 경고에만 붙는다(330번).
- 문서 덜어내기(2026-11-10): 판정 기록 규칙이 고칠 때마다 문장을 더해 무거워졌다. 스킬 문서 규칙을 AGENTS.md에 적었다(SKILL.md에는 늘 밟는 흐름만, 드문 순서는 references/, 한 규칙은 한 곳, 경위는 이 문서). playtest-verdict의 드문 순서 여섯(표본 줄이기, 판정한 가설의 문장 고치기, 이력 나중에 남기기, 다시 시험, 컨셉 되돌리기, 다른 시스템이 바뀜)을 `references/changes.md`로 옮기고 SKILL.md에는 "이럴 때 → 읽을 절" 표를 두었다. 되풀이되던 문장(여러 세션을 합친 값, 판정 에이전트가 git을 못 봄, 보정 세부)은 원본 한 곳만 남겼다. 링크와 검사 메시지가 실제 절을 가리키는지 테스트가 본다.
- 덜어내기 현장 시험(같은 날, 복사본): 새 세션이 줄인 SKILL.md에서 `changes.md`를 바로 찾아 읽었다. 그러나 "6판으로 줄이자"는 말을 결정으로 보고, 잃는 것과 요약 값을 봤는지 묻기 전에 브리프를 고쳤다. 표본 줄이기 절에 요청은 결정이 아니라는 것, 답을 받기 전에는 고치지 않는다는 것을 적었다(331번). 판정이 있는 가설은 '다시 시험할 때'처럼 지난 판정을 `cut`으로 둔다(332번). 줄인 날보다 먼저 기록한 세션이 줄인 표본을 채우면 `verdict_session_before_reduction` 오류다. 줄이기 전 표본까지 채웠으면 막지 않는다(333번). 세션 기록 전이면 이탈 메모는 보고에 두고, `before_results`는 누구라도 봤으면 `false`다(334번).
- 레벨 구성 덜어내기(같은 날): level-design SKILL.md의 게임 형태별 규칙(끊임없이 나오는 적, 끝이 정해진 라운드, 라운드로 나뉜 게임, 스테이지 선택형, 대체 맵, 보스와 곁의 무리, 회복이 없는 게임, 플레이어 행동으로만 나오는 적)을 `references/game-shapes.md`로 모으고, 경고마다 하는 일은 형식의 검사 표로 옮겼다. 형식에 따로 있던 같은 규칙(조우의 크기, 대체 맵, 스테이지 선택형)은 지웠다.
