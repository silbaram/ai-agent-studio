# 콘텐츠를 늘릴 때

[production-milestones](../SKILL.md) 2단계와 3단계에서 데이터가 바뀔 때 쓴다. 판정이 지금 데이터의 것인지 보고, 아니면 사람이 다시 플레이하거나 사용자가 이어 가기로 정한다.

## 판정의 데이터 지문

`check`는 선택한 컨셉의 가설 중 지문을 보는 가설마다 `버팀으로 판정할 때 적을 데이터 지문:` 줄을 보인다. `hypothesis <컨셉>.<가설>`은 `데이터 지문(지금)`과 본 파일을 보인다. 버팀 판정을 기록할 때 이 값을 판정의 `data`에 적는다. 판정 에이전트가 기준 지문(`criteria`)과 함께 돌려준다. 세션을 기록할 때는 데이터를 고치기 전에 `세션에 적을 게임 데이터 지문:` 줄을 세션의 `data`에 옮긴다. 플레이한 뒤 판정 전에 데이터를 고쳤으면 그 판정은 처음부터 낡은 판정이다. 지문을 무엇으로 내는지(뺀 칸, 본 파일)는 [플레이 기록 형식](../../playtest-verdict/references/playtest-record.md#판정-verdicts)의 `data` 줄, 지문이 맞지 않을 때의 코드(`verdict_data_*`, `session_data_missing`)는 [검사 내용](../../playtest-verdict/references/playtest-record.md#검사-내용)이다.

- **기대는 파일을 좁힌다.** 가설이 기대지 않는 데이터(소리 설정, 화면 문구 파일)를 자주 바꾸면 가설에 `depends_on`을 적는다([브리프](../../concept-exploration/references/brief.md)). 좁히면 지문이 바뀌므로, 판정한 가설에 더할 때는 판정 뒤 그 파일들이 바뀌지 않았는지 먼저 본다(아래 '지문 없는 판정'과 같은 방법). 확실하지 않으면 좁히지 않는다.
- **규칙 코드도 적을 수 있다.** 규칙이 데이터 밖 코드에 있으면 그 파일을 `depends_on`에 넣는다. 그때는 `data/` 파일도 함께 적는다(적은 파일만 본다).

## 지문 없는 판정

`verdict_data_missing`과 `session_data_missing`은 데이터 지문을 남기기 전에 확정한 버팀 판정이다. 근거 세션을 플레이한 뒤 데이터를 바꾸지 않았을 때만 지금 지문을 판정과 근거 세션에 적는다. 바꾸지 않았는지는 가장 이른 근거 세션의 `build` 커밋과 지금을 견준다.

```bash
git diff --stat <근거 세션의 build 커밋> -- data/
```

`depends_on`이 있으면 `data/` 대신 그 파일들을 적는다. 출력이 비었으면(또는 `playtests.json`만 나오면) 그 세션부터 지금까지 바꾸지 않은 것이다. 가장 이른 세션부터 보는 것은 세션 사이에 바뀐 것까지 잡으려는 것이다. 결과와 명령을 사용자에게 보이고 지문을 적는다. 바뀌었거나 커밋을 찾지 못하면 지문을 짐작해 적지 않는다. 사람이 마지막으로 플레이한 데이터를 알 수 없으므로 이어 가지 못하고 사람이 다시 플레이한다.

## 낡은 판정 풀기

데이터가 바뀌어 `(데이터 바뀜)`이 된 버팀 판정마다 한다. 판정 하나에 한 번씩 하고, 여러 판정을 한 회귀 파일로 묶어도 된다.

1. **봇을 다시 돌린다.** 가설 `test`가 쓰는 봇과 기준선을, 사람이 마지막으로 플레이한 빌드에서 낸 값과 같은 시드·같은 봇·같은 판 수로 지금 데이터에서 다시 돌린다. 시드만 바꿔 같은 봇을 3번 이상 돌린 범위도 함께 낸다(값이 시드로 얼마나 흔들리는지). 결과를 파일로 남긴다(예: `playtests/regression_<날짜>/result.json`). 파일에는 명령, 시드, 봇, 사람이 마지막으로 플레이한 빌드의 값, 지금 값, 시드 범위, 가설의 문턱을 적는다.
2. **판정 에이전트가 제안한다.** 회귀 파일과 가설을 주고 둘 중 하나를 받는다. Claude Code는 `studio-judge`, 판정 에이전트가 없는 환경은 같은 기준을 직접 따르고 분리되지 않았다고 보고한다.
   - **다시 플레이:** 지금 값이 시드 범위 밖에서 문턱 쪽으로 움직였다. 또는 회귀로 볼 지표가 없다(봇 기준선이 없는 가설, 자기 보고만 재는 가설). 사람이 다시 플레이하고 [playtest-verdict](../../playtest-verdict/SKILL.md)로 새로 판정한다. 플레이 전에 가설의 `builds`와 `test`의 기준선을 지금 빌드로 맞춘다([본 게임 빌드에서 다시 확인](../../production-handoff/SKILL.md#7-본-게임-빌드에서-가설을-다시-확인한다)의 2·3번). 기준 지문이 바뀌므로 [판정한 가설의 문장을 고칠 때](../../playtest-verdict/references/changes.md#판정한-가설의-문장을-고칠-때)대로 이력을 남긴다.
   - **이어 감:** 지금 값이 문턱 쪽으로 시드 범위 밖까지 움직이지 않았다. 문턱에서 먼 쪽으로 움직인 것도 이어 감이다.
3. **사용자가 정한다.** 제안과 회귀 값을 보이고 묻는다. 이어 감을 고르면 사람이 플레이한 판정을 `cut`으로 돌리고(`cut_reason`에 날짜와 까닭) 같은 편집에서 이어 간 판정을 넣는다. 결과(`holds`), 근거 세션, `criteria`는 사람이 플레이한 판정 그대로이고, `data`는 지금 지문이다. `carried.proposed`에는 판정 에이전트의 제안을 적는다. 이어 감 제안이면 판정 에이전트가 돌려준 판정을 `"status": "proposed"`로 넣고 사용자가 확인하면 `approved`로 바꾼다. 다시 플레이 제안인데 사용자가 이어 가기로 하면 `"proposed": "replay"`로 적고, `reason` 앞에 사용자의 결정과 날짜를 적어 `approved`로 넣는다. `check`의 판정 줄에 그 제안이 보이고, 출시 게이트 전에는 사람이 지금 빌드를 해 본다.

```json
{ "concept": "<컨셉 id>", "hypothesis": "<가설 id>_main", "result": "holds", "sessions": ["<사람이 플레이한 세션 id>"],
  "reason": "<더한 것> 뒤 같은 시드 봇의 <지표> <지금 값>(앞 <값>, 시드 범위 <낮은 값>~<높은 값>, 문턱 <값>). 문턱 쪽으로 범위 밖까지 움직이지 않았다",
  "criteria": "<그대로>", "data": "<지금 지문>",
  "carried": { "from": "<사람이 플레이한 판정의 data>", "regression": "playtests/regression_20261130/result.json", "proposed": "carry" },
  "status": "proposed" }
```

`carried.from`은 늘 사람이 플레이한 판정의 `data`다. 이어 간 판정에서 또 이어 가도 회귀는 사람이 마지막으로 플레이한 빌드의 값과 견준다. 조금씩 움직인 것이 쌓여 멀어지지 않게 하려는 것이다. 이어 간 판정도 그 뒤 데이터가 또 바뀌면 낡는다.

이어 가기를 되풀이하면 사람이 플레이한 지 오래된 판정이 게이트를 지난다. 이어 간 횟수를 기록의 묶음 표에 남기고, 베타로 가기 전에 사람이 지금 빌드로 다시 플레이할지 사용자에게 묻는다. 출시 후보 게이트 전에는 사람이 지금 빌드를 적어도 한 판 끝까지 한다([출시 게이트](release-gate.md)).

## 항목별로 세기

판 로그에 고를 수 있었던 항목과 고른 항목이 남으면, 항목마다 나온 횟수와 고른 횟수를 센다. 셈은 게임 쪽 분석 스크립트로 하고 결과 파일을 남긴다(`[계산: 스크립트]`). 손으로 세지 않는다.

- 한 번도 고르지 않은 항목, 나오면 늘 고른 항목을 사용자에게 보인다. 나온 횟수가 적은 항목은 그 수를 함께 보인다.
- 이것은 판정이 아니다. 고친다면 [stat-budget](../../stat-budget/SKILL.md)이나 [combat-balance](../../combat-balance/SKILL.md)로 숫자를 다시 정하고, 그러면 데이터가 바뀌어 위의 낡은 판정 풀기를 한다.
- 설계자 혼자 한 판이면 설계자가 아는 것(어느 항목이 센지)이 고르는 데 섞인다. 그 한계를 함께 적는다.
