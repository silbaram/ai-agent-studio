# 본 게임으로 넘어가기

가설이 버틴 뒤 엔진을 정하고, 그림 없는 시험판에서 본 게임으로 넘어간다. 이 스킬은 절차 문서다. 검사기가 따로 없으므로 아래 확인을 건너뛰면 아무도 알려 주지 않는다.

도구 명령은 게임 프로젝트 폴더에서 Claude Code 설치 기준(`.claude/skills/…`)으로 적었다. Codex는 `.agents/skills/…`, Windows PowerShell은 `python3` 대신 `py`([실행 경로](../studio-data/SKILL.md#실행)).

## 원칙

- **사람이 정한다.** 엔진, 시험판을 버릴지 키울지, 다시 확인의 표본, 넘어갈지는 사용자가 정한다. 에이전트는 조건과 근거, 한두 개의 추천을 내놓는다.
- **하지 않은 확인은 통과가 아니다.** 넘어가는 조건 중 하나라도 확인하지 못했으면 넘어가지 않는다. "아마 될 것"은 근거가 아니다.
- **엔진은 조건으로 거른다.** 도구나 에이전트가 다루기 편한 엔진을 기본값으로 삼지 않는다. 평판이나 인기 순위는 조건이 아니다.
- **시험판 코드를 조금씩 정리해 본 게임으로 만들지 않는다.** 키우기로 했으면 정해진 절차를 따른다.
- **판정에 쓴 도구는 본 게임에도 남긴다.** 판 로그와 봇은 다시 확인이 끝날 때까지 개발용 빌드에 둔다. 출시판에서만 뺀다.
- **기록은 한 곳.** 모든 결정은 `design/production.md`에 남긴다. 형식은 [references/production-record.md](references/production-record.md). `design/` 아래 md라 Claude Code의 편집 훅이 숫자 출처를 검사한다.

## 쓰지 않을 때

- 가설이 아직 판정되지 않았다: [playtest-verdict](../playtest-verdict/SKILL.md)로 먼저 판정한다.
- 시험판 가설이 틀렸다: [playtest-verdict](../playtest-verdict/SKILL.md#6-틀렸으면-되돌아간다)의 되돌아가기를 따른다.
- 시험판 안의 규칙을 바꿔 다시 시험한다: [다시 시험할 때](../playtest-verdict/references/changes.md#다시-시험할-때).

## 흐름

| 단계 | 사용자가 정하는 것 | 멈추는 조건 |
|---|---|---|
| 1. 넘어갈 준비 | 없음 | 조건 하나라도 못 넘거나 확인하지 못함 |
| 2. 필수 조건 | 찾은 엔진으로 계속할지, 엔진이 이미 정해졌는지 | 출처 없는 조건은 넣지 않는다 |
| 3. 후보와 엔진 시험 | 없음 | 통과한 후보가 없으면 8단계 되돌아가기 |
| 4. 엔진 고르기 | 엔진과 정확한 버전 | 사용자 답이 없으면 "선택 대기" |
| 5. 시험판 처리 | 버리고 새로 / 키워 가기 | 격리 확인이 실패하면 고칠 때까지 |
| 6. 가져갈 것과 버릴 것 | 없음 | 없음 |
| 7. 다시 확인 | 표본 크기 | `_main` 판정 전에는 게이트가 막는다 |
| 8. 넘어가기 판정 | 진행 / 되돌아가기 / 그만두기 | "확인하지 못함"이 있으면 진행하지 않는다 |

### 1. 넘어갈 준비가 됐는지 본다

7단계에서 `_main` 가설을 더하기 전에 확인한다. 아래가 모두 참이어야 한다. 하나씩 확인하고 결과를 기록의 '넘어가기 판정'에 적는다. 막혀서 멈추면 기록을 새로 만들지 않고 보고만 한다(정한 것이 아직 없다). 이미 기록이 있으면(되돌아간 뒤 다시 확인할 때) 그 표를 고친다.

```bash
python3 .claude/skills/studio-data/scripts/studio.py check . --fail-on-assumed
```

- `== data/playtests.json` 아래 "판정이 확정되지 않았거나 지금 기준의 판정인지 모르는 가설" gate 줄의 가설이 모두, 바로 위 "모름으로 둠(<가설>)" 줄에 있다. 사용자가 모름으로 두기로 정한 가설(`keep_unknown`)도 이 gate 줄에 남기 때문이다. 그 밖의 가설이 남아 있으면 버팀으로 확정되지 않은 것이다.
- 같은 곳에 "틀림으로 확정된 가설(선택한 컨셉)" gate 줄이 없다.
- `== design/concepts.json` 아래 gate 줄에 판정 기준 칸(`brief.hypotheses[…]`, `brief.prototype.success_criteria`)이 없다. 있으면 그 판정은 사용자가 정하지 않은 잣대로 낸 것이다. [playtest-verdict 1단계](../playtest-verdict/SKILL.md#1-플레이-전-가설에-id와-최소-표본을-단다)을 따라 사용자가 정한 뒤 다시 본다. 브리프의 다른 칸(경험, 범위 문장)에 남은 `[가정]`은 조건이 아니다.
- 프로젝트가 OpenSpec을 쓰는 경우, 시험판을 만든 열린 변경을 메인 스펙에 합치지 않고 닫았다([scope-guard](../scope-guard/SKILL.md)). 쓰지 않으면 "해당 없음"으로 적는다.

맨 끝 결과는 FAIL일 수 있다. 아이템·적 같은 데이터 파일의 gate 줄(숫자의 `[가정]`)도 FAIL을 내지만 넘어가는 조건이 아니다. 숫자는 본 게임에서 다듬는다. 남은 가정은 '가져갈 것'에 그대로 적는다. 모름으로 둔 가설은 본 게임에서도 모름이라는 것을 사용자에게 다시 알린다.

7단계 뒤에 이 확인을 다시 하면 판정 전인 `<id>_main` 가설이 gate 줄에 남는다. 남은 것이 `_main` 가설과 모름으로 둔 가설뿐이면 넘어가기는 그대로이고, 다시 확인이 진행 중이라는 뜻이다.

### 2. 엔진의 필수 조건을 적는다

조건은 이 게임에서 나온다. 브리프의 제약(플랫폼, 입력, 한 판 길이, 제작 규모, 엔진 후보), 가설이 요구하는 화면과 입력, 시스템 설계에서 엔진이 맡아야 하는 것을 본다. 조건마다 어디서 나왔는지 적는다. 좋아하는 언어, 써 본 적 있음 같은 주관적 이유는 필수 조건에 섞지 않고 따로 적는다.

- 먼저 게임 폴더의 엔진 프로젝트 파일로 [이미 쓰는 엔진을 알아본다](references/engine-trial.md#이미-쓰는-엔진-알아보기).
- **엔진이 처음부터 정해져 있으면**(Roblox 게임, 이미 엔진으로 만들던 게임, 사용자가 제약으로 정함) 후보를 다시 찾지 않는다. 3단계에서 후보 거르기와 추천은 하지 않는다. 지식 위험을 매기고, 엔진 시험을 그 엔진 하나로 해서 필수 조건을 모두 채우는지 확인하고 위험 목록을 적는다. 그 엔진으로 핵심 루프가 이미 도는 게임 코드가 있으면 그것을 돌려 보는 것으로 엔진 시험을 대신하고, 대신했다고 기록에 적는다. 대신한 확인은 `통과(시험판)`이다. 이때 지식 위험은 [엔진 시험](references/engine-trial.md#지식-위험)대로 적는다. 브리프 `constraints.engines`의 엔진이 `constraints.assumed`에 가정으로 적혀 있으면 정해진 것이 아니다. 사용자에게 확인한다.
- 데이터는 엔진에 묶이지 않는 JSON/CSV다. 엔진이 `data/*.json`을 직접 읽을 수 있는지를 필수 조건에 넣는다. 읽는 방법은 [엔진과 연결](../progression-economy/references/data-format.md#엔진과-연결).
- 가설의 `test`가 판 로그, 봇, 봇 기준선을 쓰면 "규칙을 화면 없이 돌려 봇과 기준선을 낼 수 있다"가 필수 조건이다. 출처는 그 가설이다. 규칙과 상태는 화면과 나뉘어 있어야 하고, 화면은 상태를 그리기만 한다. 그래야 7단계의 다시 확인이 된다.

### 3. 후보를 거르고 엔진 시험을 한다

1. 후보마다 필수 조건을 하나씩 통과·실패로 적고 근거를 단다. 공식 문서만 보고 통과로 적은 것은 `통과(문서)`, 엔진 시험에서 확인한 것은 `통과(시험)`, 같은 방식으로 만든 시험판(코드, 판 로그, 사용자의 플레이)으로 확인한 것은 `통과(시험판)`으로 적는다. 하나라도 실패하면 고르지 않는다. 탈락 사유를 남긴다.
2. 후보마다 에이전트의 지식 위험을 매겨 후보 표에 적는다. 기준은 [엔진 시험](references/engine-trial.md#지식-위험).
3. 남은 후보 중 한두 개를 추천한다. 이미 쓰던 엔진, 사용자의 경험, 지식 위험, 플랫폼 순으로 본다.
4. **엔진 시험.** 추천한 후보에서 같은 작은 과제를 만든다. 과제를 정하는 법은 [엔진 시험](references/engine-trial.md#과제). 걸린 시간, 막힌 곳, 배포 크기를 적는다. 시험 코드는 버린다(본 게임 코드가 아니다). 시험을 마치면 시험한 후보마다 [위험 목록](references/engine-trial.md#위험-목록)을 적는다.

### 4. 사용자가 엔진을 고른다

사용자가 고르면 엔진 이름과 **정확한 버전**을 적고 `[결정: 사용자 날짜]`를 붙인다. 버전은 엔진 프로젝트 파일에도 고정한다. 고정할 파일이 없는 엔진(Roblox Studio처럼 늘 최신으로 바뀌는 것)이면 기록의 '버전을 고정한 파일'에 "고정할 수 없음"과 까닭을 적고, 고를 때의 버전을 적는다. 엔진 없이 고르면 엔진 버전은 없다. 대신 빌드 도구와 언어의 정확한 버전을 적고, 본 게임의 프로젝트 파일(예: `package.json`에 범위 기호 없이)과 lock 파일로 고정한다. 본 게임 폴더가 아직 없으면 5단계에서 그 폴더를 만들 때 고정한다. 시험판의 프로젝트 파일은 고치지 않는다. 에이전트는 스스로 고르지 않는다. 사용자 응답 없이 진행하는 실행이면 후보와 시험 결과까지만 적고 "선택 대기"로 끝낸다.

### 5. 시험판을 어떻게 할지 정한다

사용자가 둘 중 하나를 고른다. 이유를 기록에 적는다.

- **버리고 새로(기본).** 본 게임은 고른 엔진에서 새로 쓴다. 시험판은 지우지 않고 그대로 보관한다(지난 판정의 근거다).
- **키워 가기.** 시험판이 이미 고른 엔진으로 되어 있고, 구조를 그대로 써도 된다고 사용자가 정한 경우만이다. 절차는 [시험판을 키워 갈 때](references/grow-prototype.md)를 따른다. 원본을 남겨 두고, 옮기는 동안 규칙과 숫자를 바꾸지 않고, 같은 시드로 원본과 새 빌드를 비교한 뒤에 바꾸기 시작한다.

어느 길이든 본 게임 코드는 보관한 시험판 코드를 가져오거나 가리키지 않는다. 찾을 경로는 기록의 '시험판 보관 위치'다(버리고 새로면 시험판 폴더, 키워 가기면 원본으로 남긴 폴더. [시험판을 키워 갈 때](references/grow-prototype.md)의 '원본을 남겨 둔다'). 본 게임 코드 폴더에서 찾은 결과가 비어야 한다. 명령과 결과를 기록의 '격리 확인'에 적는다. `git grep`은 커밋하거나 추가한 파일만 찾으므로 본 게임 코드를 먼저 `git add`한다. 리눅스·macOS·Windows PowerShell에서 같은 명령이다.

```bash
git grep -n "<찾을 경로>" -- <본 게임 코드 폴더>
```

가설의 `test`가 판 로그, 봇, 분석 스크립트를 쓰면 그것들은 시험용이지만 버리지 않는다. 본 게임의 개발용 빌드 기능으로 옮기고 7단계 판정이 끝날 때까지 둔다. OpenSpec을 쓰면 시험판 변경의 요구사항을 되살리지 않고 본 게임의 새 변경에 개발용 기능으로 적는다. 시험용 수치와 짧은 판 시간 같은 시험용 설정은 본 게임 기준에서 뺀다.

### 6. 가져갈 것과 버릴 것을 적는다

| 가져간다 | 버린다 |
|---|---|
| `data/*.json`(숫자의 단일 원본)과 숫자 출처 | 시험판 코드(버리고 새로일 때) |
| `design/concepts.json`의 브리프와 가설, `data/playtests.json`의 판정 | 시험용 수치와 시험용 설정 |
| `design/systems.json`의 시스템과 규칙 | 시험판 OpenSpec 변경의 요구사항(메인 스펙에 합치지 않았다) |
| 레벨 구성과 그레이박스 확인 항목 | |
| 플레이 기록 형식과 판 로그 형식, 봇과 분석 방법(개발용 빌드) | |

가설 없이 만드는 MVP 시스템도 목록으로 적는다. 재미를 플레이로 시험하지 않고 본 게임으로 가져가는 시스템이다. `check`의 '가설 없이 만드는 MVP 시스템' 줄의 시스템과 까닭을 옮기고, `hypotheses`에 적은 가설이 모두 모름으로 둔 가설(`keep_unknown`)인 시스템도 더한다. 그 줄에 '확인 안 함'인 시스템이 있으면 적기 전에 [system-design](../system-design/SKILL.md#6-경고를-처리한다)의 6단계로 사용자와 정한다.

남은 `[가정]` 숫자도 목록으로 적는다. 본 게임에서 맞출 값이다. 시험판에서 잰 `[측정]` 값은 시험판 빌드의 측정이다. 출처를 바꾸지 않고, 본 게임 빌드에서 다시 재면 그때 새 세션을 출처로 올린다([playtest-verdict](../playtest-verdict/SKILL.md#4-측정값을-올린다)).

### 7. 본 게임 빌드에서 가설을 다시 확인한다

시험판에서 버틴 가설이 본 게임에서도 버티는지 작은 표본으로 다시 본다. 지난 판정은 고치지 않는다. 시험판 빌드의 근거로 그대로 남는다. 화면을 만들기 전에 [art-handoff](../art-handoff/SKILL.md)를 한다.

1. 버틴 가설마다 다시 확인할 가설을 브리프에 더한다. id는 원래 id 뒤에 `_main`을 붙인다. `claim`과 `failure_signal`은 원래 문장을 그대로 옮긴다.
2. `test`도 옮기되, 시험판 빌드에 묶인 것만 본 게임 빌드에 맞춘다: 시험판 빌드로 낸 기준선 파일(본 게임 빌드에서 다시 내고 그 경로로 바꾼다), 세션 id, 문장 안의 표본 수. 판정 방법과 문턱은 바꾸지 않는다. 바꿔야 하면 다시 확인이 아니라 새 가설이므로 사용자와 정한다.
3. `builds`에 본 게임 빌드 이름을 적는다. `builds`는 세션의 `build`(커밋)나 `game_build`(판 로그의 빌드 지문) 중 하나라도 맞으면 센다. 빌드 지문을 데이터만으로 만들면 같은 데이터를 읽는 시험판과 본 게임의 지문이 같아져 시험판 세션이 섞인다. 본 게임의 판 로그는 시험판 세션에 없는 이름을 `game_build`로 남기게 한다(예: 지문 앞에 `main-`). 그 이름을 `builds`에 적는다. 화면만 바꾸면 데이터가 같아 지문도 같다. 키워 간 직후의 빌드와 가르도록 `game_build`에 화면 판을 넣는다(예: `main-ui1-<지문>`). 화면 판은 다시 확인할 화면을 만들기 시작할 때 정해 `builds`에 적고, 플레이 중에 화면을 고쳐도 바꾸지 않는다.
4. `sample`은 원래보다 작게 사용자와 정하고 `[결정: 사용자 날짜]`로 적는다. 얼마나 작게 할지는 사용자가 정한다. 원래 표본을 넘지 않는다. 정하기 전에 고를 크기마다 시험판 판을 그 크기로 묶어 같은 판정을 내 보고 사용자에게 보인다. 묶는 법과 적을 곳은 [다시 확인 표본](references/recheck-sample.md#시험판-판을-묶어-보기)이다.
5. 브리프 `prototype.success_criteria`에 더한 `_main` 가설을 적는다(예: "본 게임 빌드에서 `<id>_main`이 버틴다"). 적지 않으면 `check`가 `success_criteria_misses_hypothesis` 경고를 낸다.
6. 핵심 루프와 판 로그를 갖추고 본 게임에서 바꿀 화면과 조작이 들어간 빌드로 플레이하고 [playtest-verdict](../playtest-verdict/SKILL.md)로 기록·판정한다.

키워 간 직후의 빌드는 화면과 조작이 시험판과 같아 다시 확인의 세션으로 세지 않는다(시험판 시험을 되풀이한다). 사용자가 시험판의 화면과 조작을 그대로 본 게임에 쓰기로 했으면 다시 확인할 변화 없음이다. `_main` 가설을 더하지 않고 기록의 '본 게임 빌드에서 다시 확인'에 그 까닭과 `[결정: 사용자 날짜]`를 적는다. 플레이어에게 보이는 정보를 더하면(예: 고를 카드의 효과 미리 보기) 가설 결과가 달라질 수 있으므로 본 게임에 넣을 정보는 다시 확인 전에 넣는다. 규칙이나 숫자를 바꾸면 빌드가 바뀌므로 `test`의 기준선과 `builds`를 다시 맞춘다.

이 가설들이 판정될 때까지 1단계의 gate 줄에 남으므로, 다시 확인하지 않고 넘어가면 게이트가 알린다. 다시 확인에서 틀림이 나오면 이식에서 무엇이 달라졌는지 먼저 본다(조작감, 화면, 시간). 4번의 묶음 결과도 본다. 같은 크기 묶음에서도 틀림이 나왔으면 [틀림이 표본 크기 탓일 수 있을 때](references/recheck-sample.md#틀림이-표본-크기-탓일-수-있을-때)를 따른다. 바로 컨셉을 의심하지 않는다. 틀린 뒤 규칙을 바꾸면 [그 순서](references/rule-change.md)를 따른다.

### 8. 넘어가기 판정을 적는다

결과는 셋 중 하나이고 사용자가 정한다.

- **진행:** 본 게임을 만들기 시작한다. 개발 작업은 [scope-guard](../scope-guard/SKILL.md)로 시스템에 잇는다.
- **되돌아가기:** 확인에서 막힌 것을 풀러 앞 단계(엔진 시험, 시험판, 가설)로 돌아간다. 되돌아간 횟수를 센다. 되돌아가기가 되풀이되면 그 자체를 사용자에게 알린다. 다시 확인에서 틀려 규칙을 바꾸면 [그 순서](references/rule-change.md)를 따른다.
- **그만두기:** 이 컨셉으로 본 게임을 만들지 않는다. [컨셉을 되돌릴 때](../playtest-verdict/references/changes.md#컨셉을-되돌릴-때)를 따른다.

## 보고

- 1단계 조건마다 확인 결과(확인하지 못한 것은 그렇다고)
- 이미 쓰는 엔진을 찾은 결과(찾은 파일의 경로와 버전 단서, 없으면 없음)
- 필수 조건 표와 후보별 통과·실패와 지식 위험, 엔진 시험 결과, 위험 목록, 추천과 그 이유. 엔진을 고르라고 묻기 전에 위험 목록을 함께 보인다
- 사용자가 결정해야 할 것 한 가지(흐름 표의 '사용자가 정하는 것' 중 지금 차례인 것)
- 가져갈 것과 버릴 것, 남은 `[가정]` 목록, 격리 확인 결과

## 한계

- 검사기가 없다. 기록 형식, 필수 조건의 통과·실패, 엔진 시험, 격리 확인을 했는지는 도구가 보지 않는다. `provenance`는 숫자의 출처 표시만 본다. 기계가 보는 것은 1단계의 `check`와 7단계의 다시 확인할 가설뿐이다.
- 엔진별 절차(프로젝트 만들기, 데이터 읽기, 빌드)는 다루지 않는다. 엔진마다 확인한 적도 없다.
- 그래픽과 사운드는 다루지 않는다. 그림에 넘길 것은 [art-handoff](../art-handoff/SKILL.md)가 정리한다.
