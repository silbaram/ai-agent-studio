# 이미 만들고 있는 게임의 컨셉

이미 플레이할 수 있는 게임에 이 스킬들을 붙일 때 쓴다. 견줄 후보가 없으므로 [SKILL.md](../SKILL.md)의 1~7단계를 건너뛰고 8단계의 브리프만 적는다. 시스템 설계와 플레이 판정은 승인된 컨셉의 브리프를 읽으므로 이 컨셉이 먼저 있어야 한다.

## 순서

1. **게임을 읽는다.** 코드, 데이터 파일, 기획 문서, 사용자의 설명을 읽는다.
2. **컨셉 하나를 적는다.** `id`, `name`, `existing_game: true`를 적는다. 후보 칸(`pitch`부터 `signature`까지)과 `next_test`는 비워도 된다. 무엇을 검사하는지는 [기록 형식](concept-record.md)의 검사 표에 있다.
3. **브리프 초안을 쓴다.** 작성법은 [brief.md](brief.md)와 같다. 칸마다 어디서 가져오는지가 다르다.

   | 칸 | 가져오는 곳 |
   |---|---|
   | `loop` | 게임에서 읽는다. 지금 있는 것만 적는다 |
   | `mvp` | 지금 있는 시스템과 이번에 마저 만들 것. 7개 이하 |
   | `out_of_scope` | 문서와 사용자에게서. 코드에 없는 것을 지어내지 않는다 |
   | `experience`, `pillars`, `anti_pillars` | 사용자의 의도. 코드는 무엇이 있는지만 말하고 무엇을 노렸는지는 말하지 않는다. 초안을 쓰고 사용자에게 확인받는다 |
   | `hypotheses` | 지금 게임에서 아직 모르는 것. 사용자와 정한다 |
   | `prototype` | 가설을 시험할 다음 빌드의 범위, 기간, 성공 기준 |

4. **사용자에게 확인받고 승인한다.** 의도 칸을 사용자가 확인하면 `status`를 `approved`로 둔다. 사용자 응답을 받을 수 없는 실행이면 `proposed`로 두고 "확인 대기"로 끝낸다. 의도를 지어내 승인하지 않는다.
5. **검사한다.** `python3 .claude/skills/studio-data/scripts/studio.py check design/`

그다음은 [system-design](../../system-design/SKILL.md)이다. 밸런스 스킬을 쓰기 전에 게임 수치가 어디 있는지 본다(아래 '수치가 게임 코드에 있을 때'). 그레이박스나 단계 기록만 적는 플레이 세션은 컨셉 없이도 적을 수 있다([플레이 기록 형식](../../playtest-verdict/references/playtest-record.md)의 `concept`).

## 수치가 게임 코드에 있을 때

밸런스 스킬은 `data/*.json`을 읽고 고친다. 게임의 수치가 코드나 게임 고유 파일에만 있으면, 밸런스 스킬을 쓰기 전에 수치를 `data/*.json`으로 옮긴다. 게임이 그 파일을 읽게 고칠지, 옮긴 값을 게임에 두고 테스트로 비교할지는 [progression-economy](../../progression-economy/SKILL.md)의 작업 순서 1번을 따르고, 어느 쪽으로 할지 사용자에게 묻는다. 등급·티어·출처처럼 게임에 없는 칸은 `data/*.json`에만 적고, 정하지 않은 값은 가정(`provenance`)으로 둔다.

## 방향을 바꾸려고 후보를 만들 때

`signature`가 없는 기존 게임 컨셉은 겹침·쏠림 비교에 들지 않는다. 새 후보와 견주려면 기존 게임 컨셉에도 후보 칸과 `signature`를 채운다. `existing_game`은 그대로 둔다. 새 후보에는 이 키를 적지 않는다.
