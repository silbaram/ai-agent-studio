# 데이터 공통 규칙

게임 수치 데이터(`data/*.json`)를 다루는 스킬이 함께 따르는 규칙이다. 파일 배치와 종류 판별은 [studio-data](../SKILL.md#프로젝트-배치), 종류마다의 형식은 각 스킬의 형식 문서에 있다.

## 단일 원본 규칙

- 게임 수치와 그 효과·의도·상태·출처는 **종류별 원본 파일 한 곳**에만 쓴다(아이템은 `data/items.json`, 전투 계산은 `data/combat.json` 등). 새 게임의 시험판도 처음부터 이 파일에 둔다. 이미 코드에 있으면 [수치를 코드에서 데이터로 옮기기](#수치를-코드에서-데이터로-옮기기)를 먼저 한다.
- 카드·스킬처럼 효과가 규칙인 콘텐츠도 원본은 데이터 파일 한 곳이다. 비교하는 법은 [효과가 규칙인 콘텐츠의 비교](#효과가-규칙인-콘텐츠의-비교).
- 기획 문서와 보고서(md)는 항목을 `id`로만 언급한다. 공격력·가격·체력·비용 같은 수치를 md에 옮겨 적지 않는다. 옮겨 적으면 원본을 고칠 때 어긋나고, 거기에 결과 파일을 출처로 `[계산: …]`을 붙이면 가정값이 계산값처럼 보인다. 항목 수치는 뷰어로 안내하고, 표에는 계산 결과만 둔다.
- 보기 좋은 정리가 필요하면 문서를 생성하지 않고 뷰어(`python3 .claude/skills/studio-data/scripts/studio.py view .`)로 원본을 본다. 뷰어 사용법은 [studio-data](../SKILL.md#뷰어).

## 수치를 코드에서 데이터로 옮기기

수치가 게임 코드에만 있으면(시험판 등) 다른 점검 전에 값을 바꾸지 않고 `data/*.json`으로 옮겨 코드가 그 파일을 읽게 한다. 옮긴 뒤 빌드 지문과 시뮬레이션 결과가 있으면 옮기기 전과 같은지 확인한다. 게임이 읽는 JSON/CSV 파일을 도구도 그대로 읽는다. 게임이 그 파일을 직접 읽지 못하면(`file://`로 여는 HTML 등) JSON을 원본으로 두고 게임 파일에는 옮긴 값만 둔다. 게임 테스트가 두 값을 비교해 어긋나면 실패하게 한다. 게임 파일에서 JSON을 만들어 내지 않는다. 밸런스 스킬이 고친 값이 다음에 만들 때 덮인다.

프로젝트 폴더를 검사했는데 시스템 설계는 있고 게임 수치 종류(아이템부터 레벨 구성까지)의 파일이 하나도 없으면, 수치가 코드에만 있을 수 있어 `check`가 참고 줄로 이 절을 가리킨다. 파일이나 `design/`·`data/` 하위 폴더만 검사할 때, 읽기 오류가 있을 때, `data/`에 이 도구가 읽지 않은 JSON·CSV가 있을 때는 알리지 않는다. 수치 데이터가 없는 게임은 이 줄을 무시한다.

## 공통 필드

데이터 종류마다 항목에 아래 필드를 쓸 수 있다. 종류마다 더 쓰는 필드는 그 형식 문서에 있다.

| 필드 | 필수 | 뜻 |
|---|---|---|
| `id` | 예 | 소문자·숫자·밑줄. 같은 파일 안에서 중복 금지. 표시 이름(한글 등)은 `name`에 |
| `name` | 아니오 | 표시 이름. 뷰어에 id와 함께 보인다 |
| `intent` | 아니오 | 왜 있는가(설계 의도) 한 줄. `cut`이면 뺀 이유. 경고를 끄지 않는다 |
| `status` | 아니오 | `proposed`(제안) / `approved`(승인) / `cut`(삭제). `cut`은 비교·합계·시뮬레이션·게이트에서 빠진다 |
| `provenance` | 아니오 | `{"kind": "assumed" 또는 "computed" 또는 "measured", "source": "...", "note": "..."}`. 한글 `가정`/`계산`/`측정`도 된다. `computed`·`measured`는 `source` 필수 |
| `acknowledged` | 아니오 | 확인을 마친 경고 `{경고 코드: 확인한 이유}`. 적는 꼴과 효과는 [확인한 경고](../SKILL.md#실행). 예: `{"tier_inversion": "초반 함정 아이템으로 의도"}` |

## 효과가 규칙인 콘텐츠의 비교

피해·방어가 고정 스탯이 아니라 덱 구성, 뽑은 카드, 키워드 같은 규칙에서 나오면 [progression-economy](../../progression-economy/SKILL.md) 검사기의 점수·위협도와 [combat-balance](../../combat-balance/SKILL.md)의 처치 시간으로 판단하지 않는다. 게임 규칙 코드를 그대로 돌리는 시뮬레이터로 비교하고, 한 번에 값 하나만 바꾼다. 빌드 지문(`game_build`)은 시뮬레이터가 결과 파일 안에 남기고, 문서에는 `[계산: reports/…]`로 그 파일만 가리킨다. 태그 안에 지문을 덧붙이면 출처 경로 검사가 파일을 찾지 못한다. 그런 콘텐츠를 아이템 칸에 맞추는 법은 [progression-economy의 형식](../../progression-economy/references/data-format.md#효과가-규칙인-콘텐츠).

## 엔진과 연결

권장 방식은 데이터 파일을 게임 데이터의 단일 원본으로 두고 엔진이 직접 읽게 하는 것이다. 그러면 내보내기 단계가 사라지고 도구와 게임이 어긋나지 않는다. 아래는 일반적인 방법이며 이 저장소에서 엔진별로 검증한 것은 아니다.

- **Godot**: `FileAccess`로 읽고 `JSON.parse_string()`으로 파싱한다.
- **Unity**: `TextAsset`으로 불러 `JsonUtility` 또는 JSON 라이브러리로 파싱한다. `JsonUtility`는 최상위 배열을 직접 받지 못하므로 객체로 감싼 형식이 맞다.
- **Unreal**: DataTable은 CSV·JSON 가져오기를 지원하지만 열 이름이 행 구조체 필드와 같아야 한다. `stat.attack` 같은 열 이름은 변환이 필요할 수 있다.
- **Roblox**: JSON 문자열을 `HttpService:JSONDecode()`로 읽거나, Rojo 같은 도구로 JSON을 ModuleScript로 동기화한다.

## 같은 사실의 원본

한 사실을 여러 데이터 파일에 적으므로 어느 쪽이 원본인지 정해 둔다.

| 사실 | 원본 | 맞추는 쪽 |
|---|---|---|
| 단계 id | 전투 계산 `stages` | 레벨, 재화 흐름, 판 안 성장의 `level_at`, 시뮬레이터 설정 |
| 어떤 적이 어느 단계에 나오는가 | 전투 계산의 단계. 적의 `zone`은 처음 나오는 구역이다 | 조우의 `enemies` |
| 처치 수 | 레벨이 있으면 조우가 **처치 수의 원본**이다. 측정값이 있으면 측정값이 앞선다 | 재화 흐름의 `kills`. `--table levels` 끝의 값을 옮긴다 |
| 단계 길이 | 재화 흐름의 `duration` | 단계 표의 길이, 조우의 `at`·`duration` |
| 구매 시점 | 재화 흐름의 구매 계획 | 조우의 `purchases`가 놓인 시각 |
| 단계의 기준 장비 | 재화 흐름의 구매 계획(사는 것이면) | 전투 단계의 `player.items`. 늦게 사는 장비를 넣으면 `gear_before_purchase`가 난다 |

처치 수를 플레이 기록으로 보정하면(`calibrate`는 재화 흐름의 `kills`와 비교한다) 조우의 `repeat`도 그 값에 맞게 다시 본다.
